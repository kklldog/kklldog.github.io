# 从 Prompt Engineering 到 Harness Engineering：AI Agent 时代的“赛车与赛道”

过去这一年，大家肯定都经历过类似的“幻灭时刻”：
在各种酷炫的 Demo 里，你看着 AI Agent 行云流水地分析需求、调用 API、一键生成完整的代码，感觉整个软件工程都要被颠覆了。可是，当你满怀期望地把它接入真实复杂的业务代码库时，它就像一辆**动力狂暴但没有刹车的赛车**——一上来就横冲直撞改了几十个文件，悄悄引入了一堆不兼容的 NuGet 包，甚至为了跑通一个简单的接口，擅自把底层的依赖注入逻辑全盘推翻。

等你满头大汗地去 Revert 这些代码时，你大概会想明白一件事：**当大模型的代码生成能力不再是瓶颈时，真正的挑战变成了“我们该如何驾驭这股算力”。**

这正是目前头部 AI 团队都在讨论的范式转移——从 Prompt Engineering（提示词工程）全面走向 Harness Engineering（框架/外壳工程）。

---

### 一、 什么是 Harness？一场从“副驾驶”到“赛道设计师”的演进

如果把 AI 研发范式的演进打个比方，它就像是一部赛车发展史：

* **Prompt Engineering（提示词工程）：** 就像是**坐在副驾驶上教新手开车**。你得不停地念叨“踩离合、挂一挡、慢抬离合轻给油”。你花大量时间琢磨怎么把指令说得更精确（比如加上咒语“你是一个资深的架构师”），人和 AI 是一种强绑定的、心力交瘁的指导关系。
* **Context Engineering（上下文工程/RAG）：** 就像是**给赛车手配了高清地图和 GPS**。你告诉它：“你看，这是之前的项目文档，那是外部 API 的说明。” 它能看到更远的路况了，但如果地图太复杂或者路况突变，它照样会冲出悬崖。
* **Harness Engineering（框架工程）：** 这一次，你不再坐在副驾驶上唠叨，你变成了**高规格赛道的设计师**。
    面对一辆拥有无限马力的 F1 赛车（AI Agent），你为它修建了一条全封闭的高速公路：划定清晰的车道线、在悬崖边焊死高强度的防撞护栏、每隔一段距离设置强制进站（Pit Stop）的安检策略。

在这条赛道上，Agent 拥有绝对的驾驶自由，它可以自主规划路径、全速冲刺；但它**绝对不可能冲出你划定的物理边界**。Harness，就是包裹在模型外面的这套系统级的约束、调度与反馈框架。

### 二、 为什么在生产环境“散养” Agent 会是一场灾难？

在没有 Harness 约束的环境下，Agent 极易产生一种致命的副产品：**信任债务（Trust Debt）**。

设想一个日常场景：你让 Agent 给现有的 ASP.NET Core 项目增加一个简单的查询缓存功能。
一个缺乏“护栏”约束的 Agent 会怎么干？它可能会为了急于完成任务，直接在 Controller 里 `new RedisClient()`，而不是老老实实地去 `Program.cs` 里配置 `AddDistributedMemoryCache` 并走标准的构造函数注入。
它生成的代码当时能跑通，单元测试也绿了。但三个月后，当你准备部署到多节点的 Docker 容器环境时，这个深埋在业务逻辑里的硬编码连接就会像定时炸弹一样爆炸。

这就是大模型的“自信即兴发挥”。Harness Engineering 要解决的，就是用工程化的手段把这种野路子扼杀在摇篮里。

### 三、 把 Harness 落地：生产环境的 4 个“赛道改造”指南

理论听起来很宏大，但在实际的工程管线里“修赛道”，具体该怎么做呢？

#### 1. 扔掉百科全书，给 Agent 发放“进站路书”（渐进式披露）
**反面教材：** 把系统架构、数据库字典、部署文档一股脑拼成一个长达 5 万 Token 的 Prompt 发给 Agent。结果 Agent 经常“看串行”，或者被过时的信息误导。
**Harness 做法：** 在代码库根目录放一个极其简短的 `AGENTS.md`。
*“嘿，Agent，如果你要找数据库实体定义，去读 `src/Domain/Entities`；如果你需要了解 API 规范，去读 `docs/api-rules.md`。”*
这就像赛车比赛里的路书，让 Agent 走到哪一个赛段，就按需去读取哪一部分的上下文，保持视野清晰。

#### 2. 把代码洁癖变成“防撞护栏”（机械化约束）
不要试图在 Prompt 里苦口婆心地劝 AI：“请写出符合领域驱动设计（DDD）标准的代码”。它听不懂这种主观要求。
**Harness 做法：** 引入硬性的代码分析工具。
例如，通过配置严格的 Roslyn Analyzers 规则。当 Agent 试图在 UI 层直接调用底层的仓储层时，CI 管道会直接报红（Build Failed），并将具体的编译错误反馈给它。这时候，Agent 看到的不是人类的抱怨，而是不可逾越的物理护栏。它会根据错误日志，自动把代码重构为调用服务层接口。**你越想让 AI 自由发挥，你的 Linter 规则就必须越冷酷无情。**

#### 3. 剥夺赛车手的“自评权”（独立遥测验证）
如果你问 Agent：“代码写完没？有没有 Bug？” 它永远会满脸自信地回答：“写完了，完美运行！”
**Harness 做法：** 运动员不能兼任裁判。必须在外围挂载独立的验证流水线。比如，Agent 说它写完了一个复杂的异步 IO 处理模块，Harness 不会直接采纳，而是自动触发一套并发压力测试。只有当监控系统返回的吞吐量指标达标，且无死锁日志时，Harness 才会挥动“格子旗”，将这个任务标记为已完成。

#### 4. 设置强制 Pit Stop，打破上下文失忆
跨越数百个文件的长周期重构任务是 Agent 的滑铁卢。跑着跑着，它的上下文窗口爆了，下一秒它就忘了前半个小时干过什么，留下满地半成品。
**Harness 做法：** 引入**“握手与交接”机制**。
强制要求 Agent 在每个微小里程碑（Sprint）完成后，将当前进度和状态写入一个强类型文件（例如 `progress-state.json`）。当因为 Token 耗尽而重启一个新的 Agent 会话时，它进站的第一件事就是读取这个 JSON 文件：*“哦，上一棒已经完成了 Dockerfile 的编写，我现在需要继续处理网络挂载。”* 依靠外部存储，完美接续断层的记忆。

---

### 结语

Harness Engineering 的兴起意味着什么？

它意味着，在 AI 大跨步替代传统编码工作的今天，资深软件工程师的价值并没有被削弱，而是被**向上平移**了。
未来，衡量一个高级研发实力的标准，可能不再是你写 CRUD 接口有多快，或者你掌握了多少种设计模式；而是**你能不能在混沌的业务线里，为 AI 画出最清晰的边界，构建出最鲁棒的自动化反馈回路。**

AI 是一台拥有无限算力的引擎，而 Harness Engineering，就是你为其打造的、决定整个系统稳定性下限的顶级赛道。
